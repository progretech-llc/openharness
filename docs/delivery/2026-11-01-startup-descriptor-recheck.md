# Startup descriptor inspection candidate

A newly created Codex worker was held because its file-descriptor pool changed during inspection. The owned follow-up command reported that uncertainty as working and sent nothing. Native SessionStart later established the conversation identity. The saved incident does not identify which descriptor changed.

This source candidate allows fresh Codex discovery with an expected process identity to repeat one complete inspection after that specific pool-change error. Both inspections share the original work and time budget. The replacement inspection verifies the process, directories, descriptors and transcript headers again. A second unstable read remains held. Other evidence failures keep their existing refusal.

Owned follow-up now distinguishes unavailable inspection from a worker that is working, has a draft or needs input. An unavailable result still prevents task-file reading and sending. An inspect response can include the existing identity-hold detail. This adds no first-input sender or approval bypass. A genuinely unused native chat may require the existing owner-authorized UI bootstrap, after separately verifying ownership, an empty composer, no pending approval and no active turn. Unknown evidence alone never establishes those conditions.

The candidate is based on feature commit `0b3fe1907319468b33cca159699f986aa874ea4f`, which contains the existing owned-follow-up adapter. Live main `6856f736644ab28cbea6ef65e5c3599c2838e802` does not contain that adapter. The preliminary main-based draft is preserved at `e7ccdbbeb`. This branch preserves existing feature ancestry; it does not propose merging every feature into main. Checkout contents alone do not establish the installed binary's build provenance.
